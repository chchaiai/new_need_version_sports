# BNBU Sports 学生端业务流程（Android / iOS / Web）

> **文档版本**：v7.19
> **更新日期**：2026-08-31
> **文档范围**：本文只描述学生可见的业务规则、操作条件、状态变化和异常处理，不记录技术实现细节。
> **业务决策说明**：本文记录用户确认的目标业务规则，不表示当前产品已经全部实现。
> **Phase 3 上线状态**：本文件所述正式学生能力全部进入上线范围，不允许以空表、占位状态、Mock 或 Fake Success 代替

## 1. 学生端定位

学生端用于完成课程加入、运动打卡、记录与成绩查看、免测或校队/社团认证申请、帮助反馈和本人账号管理。

Android、iOS 与 Web 遵守同一套业务规则。不同设备可以采用不同的相机、文件选择和界面交互方式，但不能因此产生不同的学时、审核结果或成绩。

学生记录界面分别展示耐力跑真实用时和本人打卡总时长，两项独立展示，不互相折算。

## 2. 全局业务规则

| 业务事项 | 统一规则 |
|---|---|
| 学生身份 | 只有已确认的学生身份可以进入学生端 |
| 学生状态 | 只有 `ACTIVE`（已进班）和 `PENDING`（已绑定邮箱但已退班）两种 |
| 数据范围 | 学生只能查看和操作本人身份及本人课程范围内的数据 |
| 业务时区 | 统一按上海时区判断；业务日期固定为 Backend 接受 Session 开始命令时 `started_at` 在上海时区的日历日期，跨午夜、暂停、结束或延迟提交都不改变它 |
| 同学期课程 | 同一学生在同一时间只能有一个有效体育教学班；被原教师移出后可以加入其他班级 |
| 每日次数 | 同一学生在同一教学班、同一业务日期最多提交一条打卡记录 |
| 默认结果 | 学生成功提交打卡后，记录默认有效 |
| 最短计入 | 少于 60 分钟可以结束，但计入学时为 0小时  |
| 单次计入 | 满 60 分钟但不足 120 分钟计 一小时有效打卡；达到或超过 120 分钟计 两小时有效打卡 |
| 学期目标 | 当前统一总目标为 20 小时；学生只能在系统唯一当前学期内产生新的业务事实 |
| 分类目标 | 责任教师分别设置课程相关运动和其他运动目标，两类合计固定为 20 小时 |
| 打卡总时长 | 两类计入完成量之和；每类最多计到本类目标，单类超额不能替代另一类 |
| 达标后行为 | 打卡总时长达到 20 小时后停止新打卡 |
| 审核结果 | 打卡只存在有效和无效两种当前结果 |
| 位置数据 | 当前不采集定位、轨迹或地图信息 |
| 历史保留 | 课程关系、打卡、凭证、审核和成绩历史不能由学生物理删除 |
| 审计留痕 | 正式审计日志属于上线范围；关键学生业务操作形成不可修改的审计事件，但学生不能访问系统级原始事件、安全元数据或服务器运行日志 ZIP |
| 站内通知 | 正式结果变化进入站内通知中心；不发送短信、邮件或 Android/iOS 系统 Push，通知是否已读不改变业务结果 |
| 正式产品入口 | 不提供“模拟扫码成功”、`Fake Success` 或合成/Mock 学生工作区作为正式入口或成功路径 |
| 运动记录重提 | 已提交记录不建立 `resubmission` 或 attempt 链；教师通过追加判断纠正，学生下一业务日期创建独立的新记录 |
| 版本策略失败 | 单个版本策略辅助接口故障不独自阻断整个 App；已缓存的强制升级要求不能因此被清除、降级或绕过 |

## 3. 主要业务入口

| 入口 | 学生可完成的事项 |
|---|---|
| 首页 | 查看当前学期、课程摘要、分类进度、当前成员状态和常用入口 |
| 课程 | 查看已加入课程，扫码或输入邀请码加入课程 |
| 打卡 | 开始、暂停、继续和结束运动，采集凭证并提交记录 |
| 记录 | 查看耐力跑真实用时或免测状态，以及本人打卡总时长 |
| 运动进度 | 查看两类运动目标、有效学时、认证认可学时、剩余学时和成绩 |
| 我的 | 管理邮箱、偏好、隐私、帮助、反馈和本人账号 |

## 4. 启动与系统模式

学生端启动后：

1. 读取本人已保存的语言、主题和必要偏好；
2. 检查当前版本策略；
3. 取得当前系统模式；
4. 有有效登录状态时恢复本人身份；
5. 登录状态失效时返回登录或课程邀请入口；
6. 按当前系统模式决定可进入的页面和可执行的操作。

版本策略检查是启动辅助检查。单个辅助接口本次故障本身不能使整个 App 不可用；但本机已经缓存强制升级要求时，本次检查失败不得清除、降低或绕过该要求。客户端只有取得新的权威版本策略结果后，才能按新结果更新已保存的要求。

| 系统模式 | 枚举 | 学生端行为 |
|---|---|---|
| 正常模式 | `NORMAL` | 按本人身份、课程成员关系、资源归属和业务状态完成已开放业务 |
| 维护模式 | `MAINTENANCE` | 暂停普通业务访问，只展示管理员发布的中英文维护公告和预计恢复时间 |

进入维护模式前尚未完成提交的内容不会自动成为正式业务记录，也不得被显示为已提交；是否存在本地草稿及其保留方式仍按对应页面既有草稿规则处理，系统模式本身不作额外承诺。预计恢复时间只用于告知，不会让客户端自行解除维护限制；授权管理员明确切换到正常模式后，学生端重新取得系统模式和最新业务状态，再开放相应入口。

学生不能通过修改本机时间、缓存、旧页面状态或重复请求绕过系统模式限制。模式切换不删除或改写学生已有的课程成员、打卡、审核、认证、免测、成绩、反馈或账号事实。

## 5. 登录与账号

### 5.1 已有学生登录

已有学生使用已验证的学校邮箱和一次性验证码登录。

当前学生端不使用手机号或短信登录，也不设置传统登录密码。连续输入错误或频繁申请验证码时，系统可以暂时限制继续尝试。

### 5.2 新学生通过课程邀请建立账号

1. 学生扫码或输入邀请码；
2. 查看教学班、课程、教师、学期和邀请状态；
3. 填写姓名、学号、性别和年级；
4. 确认加入；
5. 系统检查当前学期是否已经存在有效体育教学班；
6. 条件满足时建立学生身份和有效课程成员关系；
7. 学生绑定并验证学校邮箱；
8. 完成后进入课程和首页。

正常加入不需要教师或管理员审批。

如果学生在当前学期已经存在有效体育教学班，新的加入必须拒绝。原责任教师将学生移出原教学班后，只要学生当前没有其他有效体育教学班，就可以通过新邀请加入其他教学班。

### 5.3 邮箱绑定与换绑

- 首次绑定时，新邮箱必须完成验证码确认；
- 更换已验证邮箱时，当前邮箱和新邮箱都需要验证；
- 无法访问当前邮箱时，学生联系学校体育部门或管理员完成身份核验；
- 仅修改页面显示不能改变已验证邮箱。

### 5.4 学生状态

学生状态只描述当前课程成员关系，不描述邮箱绑定流程、登录会话或身份恢复申请：

- `ACTIVE`：学生已绑定并验证学校邮箱，当前处于有效体育教学班中，页面显示“已进班”；
- `PENDING`：学生已绑定并验证学校邮箱，但已被责任教师移出且当前没有有效体育教学班，页面显示“已退班”。

学生正常加入或被原责任教师恢复到教学班后，状态从 `PENDING` 变为 `ACTIVE`；责任教师将学生移出当前教学班后，状态从 `ACTIVE` 变为 `PENDING`。首次邮箱绑定完成前使用的临时认证状态不属于学生状态；身份恢复申请也是独立事项，不能把学生状态改成 `RECOVERY_REQUIRED`、`DISABLED` 或其他枚举。

学生首页的体育学时进度标签必须受当前学生状态约束：只有 `ACTIVE` 学生可以显示“进行中”；`PENDING` 学生显示“已退班”，即使本地缓存或旧进度快照仍带有进行中字段，也不得继续显示“进行中”。`ACTIVE` 学生已经达标时可以显示“已达标”。Web、Android 与其他学生端遵守同一显示语义。

### 5.5 退出登录

退出登录后，当前设备的登录状态失效，并清除本机保存的身份凭据。

### 5.6 注销本人账号

账号注销需要再次验证本人身份。

1. 学生查看注销影响；
2. 使用当前已验证邮箱接收验证码；
3. 输入验证码并确认注销；
4. 系统检查是否存在进行中的运动或其他阻塞事项；
5. 条件满足时删除本人登录账号、密码凭据、现有登录会话、验证码/验证挑战、学校邮箱以及当前学生资料中的姓名、学号等账号相关数据；
6. 所有设备退出登录，原账号不能继续登录或被静默恢复；
7. 返回登录页。

注销不删除必须保留的课程关系、运动记录、正式媒体、审核、成绩和审计历史。这些保留事实只能关联一个不具登录能力且不含当前账号资料的内部历史主体标识，不能借此恢复已删除账号。

### 5.7 管理员只读查看边界

管理员可以在“用户与账号”页面搜索、筛选并查看学生必要资料和当前学生状态，但不能在该页面修改学生姓名、学号、性别、年级、学院、专业、班级、邮箱、角色、学生状态、课程关系或登录状态。学生列表和详情只显示 `ACTIVE` 或 `PENDING`；待核验身份恢复申请是独立事项，不作为学生状态，也不代表管理员可在学生详情直接批准、驳回、改绑或恢复账号。

## 6. 课程加入与查看

### 6.1 加入课程

学生可以扫描课程二维码，也可以手动输入邀请码。两种方式遵守相同的预览、确认、同学期唯一教学班和直接入班规则。

成功加入后，学生立即成为该教学班的有效成员，不进入等待教师审批状态。

初版班级必须由责任教师创建并生成邀请码。学生只能通过有效邀请码加入，不能自行创建班级、从未授权的班级目录自由选择班级或把本地选择当作正式成员关系。

正式产品不提供“模拟扫码成功”、`Fake Success` 或合成/Mock 学生工作区入口。开发或测试入口即使展示加入后的页面，也不能建立课程成员关系，不能写入正式业务事实。

### 6.2 课程列表与详情

学生只能查看本人课程成员关系范围内的信息，包括：

- 教师自定义的课程名称；课程代码和教学班号不属于学生端业务信息；
- 当前学期和责任教师；
- 允许打卡的日期或时间范围；
- 课程相关运动目标；
- 其他运动目标；
- 本人的课程成员状态；
- 本人的打卡、认证认可学时和成绩摘要。

学生课程页只展示当前有效课程关系，不使用“已结束”课程状态。管理端目录的 `UPCOMING` 或 `ACTIVE` 及其成员、打卡、目标和时长汇总只用于管理员了解当前课程运行，不开放单条打卡或媒体处理，也不能改变学生的课程成员关系、入班资格或打卡结果。

管理员只有在目标 `UPCOMING` 学期已经到达开始日期后才能确认切换；切换成功后旧学期归档，新学期成为唯一当前学期。学生只能在新的当前学期产生后续业务事实，既有课程、打卡、申请和成绩历史不被改写。

学校官方名单是教学管理快照，不等同于学生已经加入课程。

### 6.3 学生不可执行的课程动作

- 不能自行退出课程；
- 不能删除课程成员历史；
- 不能自行转班；
- 不能恢复已被教师移出的成员关系；
- 责任教师账号被管理员删除时，本人的课程关系和全部业务历史继续保留；删除不以责任教师交接为前置，管理员不能修改或转移课程责任教师，已有课程继续引用不具登录能力且不含当前账号资料的内部历史主体；
- 不能在已经存在有效体育教学班时同时加入第二个教学班；
- 不能通过修改本地课程信息制造已加入、已退课或已转班状态。

## 7. 运动打卡

### 7.1 开始前条件

学生开始运动前必须满足：

- 账号和学生身份有效；
- 当前学期只有一个有效体育教学班；
- 当前处于该教学班允许打卡的时间范围；
- 当前没有另一条进行中的运动；
- 本学期打卡总时长尚未达到 20 小时；
- 系统当前允许业务写入。

达到 20 小时后，学生端提示“已达到 20 小时，本学期无法继续打卡”，并停止创建新运动。

### 7.2 运动状态

运动会话按以下顺序变化：

- 开始后进入进行中；
- 进行中可以暂停；
- 暂停后可以继续；
- 进行中或暂停状态可以结束；
- 结束后不能重新变回进行中。

学生端计时器只用于即时显示。正式实际运动时长由 Backend 累计全部 `ACTIVE` 区间，`PAUSED` 区间完全排除；切换后台、断网、重启设备或修改设备时间不能改变 Backend 认定的正式实际运动时长。

正式实际运动时长描述运动事实，计入有效学时描述该事实经过业务分档后对进度的贡献。两者是不同业务概念，学生端不得把 0、60 或 120 分钟计入有效学时显示成 Backend 认定的正式实际运动时长，也不得反向使用计时器显示值直接决定有效学时。

本次运动的业务日期由 Backend 在接受 Session 开始命令时按 `started_at` 的上海日期固定。跨午夜、暂停、结束或延迟提交不会改变该日期，学生端不能上传或改写业务日期。

正式学生业务不提供“增加 60 分钟”。

### 7.3 结束与学时分档

| 实际持续时间 | 计入学时 |
|---|---:|
| 少于 60 分钟 | 0 分钟 |
| 60 分钟至不足 120 分钟 | 60 分钟 |
| 达到或超过 120 分钟 | 120 分钟 |

单条记录按正式实际运动时长映射出的计入有效学时只有 0、一小时 或 两小时。达到最低门槛的记录只映射为 1 小时或 2 小时，不产生 1.5 小时等小数档；0 小时档只对应正式实际运动时长不足 60 分钟。当前审核结果为 `INVALID` 时不改写原分档结果，只让该 Record 当前对所有学时统计贡献为 0；恢复为 `VALID` 后继续使用原分档结果。

学生和教师都不能手工改写正式时长。

### 7.4 运动分类与说明

- 课程相关运动和其他运动均必须填写运动说明；去除首尾空格后，说明长度必须为 1 至 200 字；
- 学时进入对应分类；
- 两类目标由责任教师设置；
- 两类目标合计固定为 20 小时；
- 学生需要补足认证认可学时之外的分类目标。

### 7.5 媒体凭证

每条打卡记录至少保留一项有效媒体凭证。

| 媒体类型 | 业务规则 |
|---|---|
| 图片 | 0 至 6 张；只允许 JPEG、PNG；单张最大 10 MB |
| 视频 | 0 至 1 段；只允许 MP4；长度 1 至 15 秒并包含音轨；单段最大 100 MB |
| 组合方式 | 允许照片和视频同时提交，但每条记录至少需要一项有效媒体凭证 |
| 提交范围 | 本次保留的照片和视频全部随本次打卡提交 |
| 单条总大小 | 本条 Record 全部媒体文件合计最大 250 MB |

系统相机或录像界面确认拍摄完成后，素材直接加入本次运动的本地凭证列表，不再显示额外的“确认保留”弹窗。学生点击某一项凭证可以预览；如果觉得不合适，可以在正式提交开始前删除该单项凭证。删除只移除尚未上传的本地草稿，该素材不参与本次提交；删除后仍可重新拍摄，但提交时必须至少保留一项有效凭证。

正式提交或媒体上传开始后，学生不能再从客户端删除凭证。提交成功后，凭证成为正式记录的一部分，不能由学生、教师或管理员通过普通业务页面删除或改写。

Android 和 Web 必须在上传前校验媒体格式、数量、单文件大小和单条 Record 总大小，并在不满足条件时阻止上传。Backend 必须再次执行权威校验，不得仅信任客户端声明或客户端校验结果；超过任一限制的媒体不能进入正式 Record，也不能显示为正式提交成功。

媒体必须来自本次运动，能够支持责任教师判断真实性和内容是否合规。处理图片时应移除定位等不必要的隐私信息。

### 7.6 记录提交与默认有效

1. 学生结束运动；
2. 选择运动分类并填写必要说明；
3. 逐项预览并删除不合适的照片或视频，确认列表中只保留准备提交的凭证；
4. 系统检查当日唯一性、分类、说明和媒体；
5. 学生提交记录；
6. 记录默认有效；
7. 对应分类学时进入当前进度。

提交成功后不进入待审核状态。

### 7.7 教师判定无效后的处理

责任教师发现凭证或内容不符合要求时，可以修改为无效判断。

无效后：

- 该记录不再贡献学时；
- 原记录、原媒体和审核历史保持不变；
- 学生不能撤回或编辑原记录；
- 当日提交名额不恢复，系统不提供恢复当天第二次打卡机会的机制；
- 学生只能在下一个符合条件的业务日期重新运动和提交。

责任教师发现先前判断有误时，可以追加新的有效判断纠正，但不能覆盖历史。纠正为有效后，该记录原本确定的有效一小时或 有效两小时重新参与进度汇总；审核切换不得清零、重算或改写原计入时长。

系统不为原记录创建 `resubmission` 或新的 attempt。学生在下一业务日期提交的是独立的新记录，不是对原记录的重提。

## 8. 记录、进度与成绩

### 8.1 学生记录界面

记录界面展示两个独立内容：

1. 耐力跑真实用时或免测状态；
2. 本学期打卡总时长。

耐力跑真实用时不折算成打卡时长，打卡时长也不替代耐力跑真实用时。

### 8.2 分类进度

学生可以分别查看：

- 课程相关运动目标；
- 课程相关运动实际有效学时；
- 课程相关运动认证认可学时；
- 课程相关运动剩余学时；
- 其他运动目标；
- 其他运动实际有效学时；
- 其他运动认证认可学时；
- 其他运动剩余学时；
- 两类合计打卡总时长。

每类计入完成量最多达到该类目标。某一类实际运动超过本类目标的部分可以留在历史记录中，但不增加打卡总时长，也不能替代另一类尚未完成的目标。

### 8.3 运动进度参考与最终成绩

当前 20 小时规则生成运动进度参考：

- 两类目标合计固定为 20 小时；
- 实际有效学时和认证认可学时共同计入对应分类；
- 每类计入完成量最多达到本类目标；
- 打卡总时长等于两类计入完成量之和；
- 单类超额不能替代另一类未完成部分；
- 达到 20 小时后进度状态为已达标；
- 未达到 20 小时时生成完成比例参考；
- 未达标结果不能显示成已达标；
- 耐力跑真实用时独立展示，不进入 20 小时进度参考；
- 责任教师可以填写任意 `INT` 整数最终成绩，系统不额外限制为 0 至 100，最终成绩也不要求等于进度参考结果；
- 每次发布可以附带可选备注，备注最多 50 个字符；
- 学生端展示责任教师最近一次发布的最终成绩及其备注，不在本地生成或改写最终成绩。

责任教师可以直接填写、修改并重新发布最终成绩，不需要学生发起成绩调整申请，也不需要管理员审批。历次发布结果继续保留。

### 8.4 上线学时统计

上线统计累计当前审核结果为 `VALID` 的 Record 和当前有效的认证认可学时。每条 Record 根据 Backend 确认的正式实际运动时长映射为 0、一小时或两小时计入有效学时；当前审核结果为 `INVALID` 时，该 Record 不计入任何学时统计；认证被撤销后，相应认可学时不再贡献进度。

系统先在每个运动类别内累计有效学时，并按照该类别目标上限封顶，再将各类别封顶后的有效学时相加得到总有效学时。课程完成率为 `min(总有效学时 / 总目标学时, 100%)`。学生端把比例四舍五入为整数百分比展示，但是否达标、是否允许继续打卡和全部其他业务判断只使用原始分钟值，不使用展示百分比。

## 9. 耐力跑、成绩换算、免测与校队/社团认证

### 9.1 耐力跑真实用时

女性展示 800 米真实用时，男性展示 1000 米真实用时。真实用时由责任教师根据正式测试结果确认。

### 9.2 耐力跑成绩换算

责任教师确认真实用时后，系统根据学生性别和当前年级组自动选择换算表：男生使用对应年级组的 1000 米表，女生使用对应年级组的 800 米表；大一/大二和大三/大四分别计算。真实用时以整数秒匹配一个包含上下限的连续区间，学生查看对应的 0 至 100 分和优秀、良好、及格或不及格等级。

当前预置表中，99 分至 1 分按连续 3 秒一档、每档下降 1 分；100 分和 0 分覆盖首尾区间。换算结果只能来自唯一匹配区间，不能由学生手工选择、修改或在本地估算；资料不足或没有唯一匹配规则时显示不可用，不得猜测分数。

耐力跑换算分和等级不增加打卡总时长、不进入 20 小时运动进度参考，也不自动成为或改写责任教师发布的最终成绩。管理员调整换算表后，已经形成的本人历史换算结果和已发布最终成绩继续保留。

### 9.3 耐力跑免测

学生提交耐力跑免测申请和证明材料，由责任教师审核。证明材料只接受 JPEG、PNG 或 WebP 图片，不接受 PDF、视频或其他文件格式；同一份申请的首次提交和全部补充提交合计最多 3 张，单张最大 10 MB。学生可以拍照或从相册选择符合规则的图片，并在申请详情中查看已上传图片的缩略图。

批准后，学生记录界面的耐力跑位置显示免测，不显示真实用时，也不按普通用时换算表生成分数或等级；免测不增加打卡总时长、不改变 20 小时进度参考，也不会自动改写教师已发布的最终成绩。

### 9.4 校队和社团认证

学生提交校队或社团证明材料，由责任教师审核。证明材料沿用耐力跑免测的图片规则，只接受 JPEG、PNG 或 WebP；同一份申请的首次提交和全部补充提交合计最多 3 张，单张最大 10 MB，并在申请详情中展示缩略图。

批准后，责任教师自定义认可总时长，并按实际情况分配到：

- 课程相关运动认可学时；
- 其他运动认可学时。

课程相关运动和其他运动都可以获得认可学时，任一类可以为 0，不固定只抵扣某一类。每类认可学时不能超过对应分类目标，两类合计不能超过 20 小时。学生仍需完成没有被认可的剩余分类学时。

认证被撤销后，相应认可学时取消，学生需要补足差额。历史继续保留。

## 10. 站内结果、偏好、帮助与反馈

### 10.1 站内结果

学生在对应页面查看课程成员、打卡审核、免测、认证、耐力跑和成绩结果。

成员关系、打卡审核、免测、认证、耐力跑、最终成绩、反馈处理以及系统维护或恢复等面向本人的正式结果变化进入站内通知中心。系统不发送短信、邮件或 Android/iOS 系统 Push；通知是否已读不改变业务结果，业务是否完成仍以对应页面显示的正式状态为准。

### 10.2 偏好

学生可以调整本人支持的语言、主题和界面偏好。偏好不能改变身份、课程关系、审核结果或成绩。

### 10.3 帮助中心

学生可以从本人设置进入帮助中心，按当前客户端语言取得管理员已经发布的帮助文章，并按客户端提供的搜索和分类方式查看标题、正文及分类。每次只返回当前语言投影，不同时暴露中英文编辑源；切换客户端语言后重新取得对应语言内容。学生不能查看草稿、已下线文章、管理关键词、排序权重或审计信息。

只有状态为已发布 `published` 的文章属于当前正式帮助文章。草稿 `draft` 从未公开；文章变为已下线 `archived` 后停止公开，但不会删除管理端历史。客户端因加载失败而展示最近缓存时必须明确标识为缓存内容，不能把缓存中的旧文章冒充为当前仍已发布；加载恢复后重新以服务端当前结果为准。

帮助文章只用于解释既有业务规则，不能授予权限、改变课程成员、打卡、审核、认证、免测、成绩、反馈或账号事实。文章内容与对应业务页面冲突时，以权威业务流程和对应页面的正式状态为准。

“维护期间操作”分类的帮助文章是普通自助说明，不是当前维护公告。系统进入维护模式后，实时维护公告和预计恢复时间由系统模式流程展示，学生不能把帮助文章中的日期或说明当作当前系统状态。

### 10.4 服务反馈

Android 与网页学生端统一提交问题类型（功能异常、功能建议、无障碍问题、隐私问题、其他）和问题描述。系统把反馈与已登录学生身份关联，生成反馈编号、提交时间和初始状态“待受理”；管理端按同一分类与问题内容展示，并补充提交人姓名、学号和当前学校邮箱。客户端平台、版本、附件、优先级、指定处理人和内部备注不属于当前管理界面的业务字段。

负责处理反馈的分管理员由总管理员使用独立账号、姓名、有效且唯一的学校邮箱、可选所属部门、初始密码和至少一项业务权限建立，创建后默认启用。学生问题反馈是 8 项可分配权限之一；系统概览自动可见，分管理员设置不能下放。总管理员可以编辑权限、停用、重新启用或删除分管理员，但删除前必须先移交职责，且不会清除已经完成的学生反馈或审计历史。该治理方式不改变学生提交和查看反馈的流程。

学生提交反馈后，反馈统一进入管理员队列。学生可以查看本人反馈的当前状态和管理员公开回复，但不能选择处理状态、代替管理员回复、删除处理记录或指定处理人。

反馈状态依次表达当前处理阶段，但不是固定的单向审批链：待受理表示尚未开始处理，受理中表示管理员正在跟进，待技术团队处理表示需要技术排查，处理完成表示当前已经给出处理结果，已关闭表示本轮反馈结束。管理员首次处理待受理反馈时默认进入受理中；以后每次保存状态都必须同时新增一条学生可见回复。处理完成或已关闭后确需继续跟进时，管理员可以重新设为受理中或待技术团队处理，并新增说明，已有记录继续保留。

课程问题需要教学事实时，由管理员另行协调责任教师核查；当前反馈界面不建立面向教师的转交或指派关系，反馈状态和公开回复仍由管理员维护。反馈本身不能直接修改打卡、成绩、申请、账户状态或课程关系，学生仍须以对应业务页面的正式结果为准。

## 11. 异常与隐私

- 重复点击不能产生重复课程关系、打卡或申请；
- 数据已被其他操作更新时，学生先查看最新状态；
- 登录状态失效时返回登录页；
- 本地草稿不代表已经提交成功；
- 错误上报不得包含密码、验证码、完整身份资料或媒体内容；
- 学生不取得系统级原始审计事件、安全元数据或服务器运行日志 ZIP；系统内部留痕不能向学生暴露其他用户、管理员或教师的信息；
- 系统不设置教师内部备注；教师审核只产生正式结果和学生可见的原因或处理意见；
- 学生不能获得媒体内部存储信息；
- 当前不收集定位、轨迹或地图信息。

## 12. 明确不属于学生端的能力

- 手机号或短信登录；
- 学生自助密码找回；
- 教师或管理员审批正常入班；
- 同一时间加入多个有效体育教学班；
- 学生自主退课或转班；
- 撤回或改写已经提交的打卡记录；
- 对已提交运动记录创建 `resubmission` 重提或 attempt 链；
- 手工增加 60 分钟；
- 手工覆盖正式运动时长；
- 待审核、审核中或申诉审核形式的打卡状态；
- 达到 20 小时后继续新打卡；
- 定位轨迹、地图展示和位置策略；
- 用耐力跑真实用时增加打卡总时长；
- 成绩调整申请；
- 查看、筛选或下载系统级原始审计事件和服务器运行日志 ZIP；
- 依赖站内通知是否生成或已读来判定业务完成；
- 在正式产品中使用“模拟扫码成功”、`Fake Success` 或合成/Mock 学生工作区作为入口或成功路径。

## 13. 学生端主流程

1. 已有学生使用学校邮箱验证码登录；新学生通过课程邀请填写资料并直接加入教学班。
2. 加入前确认当前学期没有其他有效体育教学班。
3. 查看教师设置的两类运动目标。
4. 选择有效教学班，确认尚未达到 20 小时后开始运动。
5. 根据需要暂停或继续，完成后结束运动。
6. 选择运动分类，填写必要说明，保留合规照片和/或短视频。
7. 提交打卡，记录默认有效。
8. 教师可以根据凭证追加无效或有效判断。
9. 学生查看两类进度、认证认可学时、打卡总时长和耐力跑真实用时。
10. 达到 20 小时后停止新打卡。
11. 教师查看运动进度参考，填写并发布最终成绩。
12. 学生可以提交耐力跑免测、校队或社团认证申请。
13. 学生在对应页面查看结果，并通过管理员统一反馈入口寻求帮助。
