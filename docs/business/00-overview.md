### 0.1 决策状态语义

| 状态 | 含义 | 下游约束 |
|---|---|---|
| `ACCEPTED` | 已由业务负责人确认的业务真相 | 可以作为数据库和 Contract 的业务输入 |
| `PENDING` | 仍需业务负责人决定 | 不得进入数据库、Contract 或客户端/Backend 实现；涉及的能力不得进入上线范围 |
| `REJECTED` | 已明确否决的业务方案或能力 | 不得作为正式产品能力恢复 |

除非正文或本节登记表明确标记为 `PENDING` 或 `REJECTED`，本文件及三份角色业务文档中以“必须”“可以”“不能”等规范性语言记录的现行业务规则均为 `ACCEPTED`。各文档“明确不属于”“已删除的业务”章节中的能力为 `REJECTED`；明确写为“当前不处理”的场景不进入上线范围，也不得据此补造业务规则。

#### 0.3.1 `P5E-NBD-01`：Teacher Dashboard“需要关注的打卡记录”（ACCEPTED）

决策前已确认事实：

1. Record 提交成功即默认 `VALID`，不存在待审核状态；责任教师只在发现问题后追加 `INVALID`，不逐条批准所有正常 Record。
2. 当前正式审核投影只有 `VALID / INVALID`，每次教师判断只追加，当前结果可以由后续判断纠正。
3. Phase 5E 开始时教师工作台列出“需要关注的打卡记录”，但四份业务权威没有定义判定集合、计数和下钻。
4. 固定 `1.1.0-contract` 的 `TeacherDashboard` 没有对应数量；课程 Record 列表只能按单个 `courseId` 查询，并可按当前 `reviewResult=VALID/INVALID` 筛选，没有教师全局精确总数。
5. 当前 Domain/数据库已有 `RecordReviewState.currentResult`、Course 归属和责任教师范围，可以计算当前 `INVALID`；没有异常风险分、自动风险原因或独立“需要关注”状态。

决策前缺失规则：判定条件；是否只看当前学期和未关闭课程；学生后来被移出是否影响既有 Record；按 Record、学生还是 Review 事件计数；计数时点；纠正为 `VALID` 后是否离开集合；点击后进入哪个页面和预置哪个筛选。

#### 0.3.2 `P5E-NBD-02`：Teacher/Admin 密码与权限（ACCEPTED）

当前已确认事实：

1. 教师批量建立时的初始密码为至少 8 位且包含大写字母、小写字母和数字；教师首次登录后必须先设置个人密码。
2. 教师忘记密码时通过已验证学校邮箱完成本人验证；管理员不能查看教师个人密码，也没有代教师重置密码的正式业务。
3. 分管理员初始密码只要求非空且两次一致；所有由他人或系统分配的 Teacher/Admin 初始密码都是临时密码，首次登录必须先由本人修改；总管理员不能代设分管理员个人密码。
4. 总管理员和分管理员都可以通过已验证学校邮箱找回密码，成功后旧登录状态全部失效；找回页不要求用户输入组织代码。
5. 固定 Contract 已有 `changeOwnPassword`（Teacher/Admin、本人、当前密码、允许维护模式、撤销其他 session）和 `resetPassword`（匿名、Teacher/Admin 的已验证邮箱 challenge、撤销全部旧 session），但两类个人新密码都只约束非空。
6. Domain/数据库已有通用 `password_credential.must_change`、`password_version`、PHC hash、challenge digest 和 session revoke 能力；没有密码历史或独立密码策略表。

当前缺失规则：无。Phase 5E 已明确个人密码只要求非空，不设置最大长度、弱密码名单或“必须不同于当前密码”的限制；首次改密、本人改密、邮箱自助重置、停用/删除账号、会话失效、管理员代设边界、定期轮换和稳定错误均已确定。

统一权限、会话和错误包的确认结果：

1. `ACCEPTED`：`changeOwnPassword` 只允许状态为 `ACTIVE` 的 Teacher/Admin 本人使用，不需要任何管理员业务权限，要求有效 session、当前密码和最新 version；维护模式仍允许。成功后撤销其他 session，当前 session 保留，并清除本人首次改密门禁。
2. `ACCEPTED`：`resetPassword` 只服务 Teacher/Admin，通过已验证学校邮箱的 `PASSWORD_RESET` 一次性 challenge 完成本人重置；请求 challenge 始终反枚举，不要求组织代码。成功后撤销全部 session、不自动登录，并清除首次改密门禁。`DISABLED` 或已删除账号不能借重置恢复访问；停用账号在已验证 proof 后返回稳定停用错误，删除账号继续保持反枚举失败。
3. `ACCEPTED`：密码内容、验证码和 Token 不进入普通日志、业务记录或 AuditEvent；只记录不含秘密的安全动作、结果和 request ID。
4. `ACCEPTED`：继续使用现有 `INVALID_CREDENTIALS`、`CHALLENGE_EXPIRED`、`ACCOUNT_DISABLED`、`FIRST_PASSWORD_CHANGE_REQUIRED`、`VERSION_CONFLICT` 和 `RATE_LIMITED`；challenge 请求统一使用 202 反枚举外观。删除 `TOO_LONG / BLOCKLISTED / SAME_AS_CURRENT` 及其对应限制，不新增 `PASSWORD_POLICY_VIOLATION`；非空 request 校验继续使用既有请求校验错误。
5. `ACCEPTED`：不做任意周期强制改密；只有本人请求、首次临时密码、管理员明确停用/安全处置或有 credential 泄露证据时才触发必要变更。

`P5E-NBD-02` 已全部关闭。Portal 当前私自使用的“至少 12 位”以及任何最大长度、blocklist、密码历史或“不得与当前密码相同”校验都不是业务规则，不得作为隐式 fallback 恢复。

Contract 判断：`PWD-POLICY-A` 本身大体匹配当前非空 schema；但 `PWD-FIRST-B` 要求把首次改密 gate 扩展到 Admin，`PWD-ADMIN-B` 要求删除 `UpdateSubAdminRequest.newPassword/confirmNewPassword`，已接受的 reset 停用错误与 gate 清除也需要明确 wire 语义。因此密码规则需要在独立后续阶段产生新的 Contract CR；本阶段仍不修改 Contract 或创建 CR 文件。

上线版本必须完整提供以下正式流程：

1. 管理员登录，创建并维护当前学期；
2. 管理员创建或导入教师账号；
3. 教师登录并创建本人负责的班级；
4. 教师为班级设置两类运动目标并生成邀请码；
5. 学生通过有效邀请码建立或使用本人身份并加入班级；
6. 学生开始运动，在 `ACTIVE` 和 `PAUSED` 间切换并结束运动；
7. 学生填写运动分类和说明，保留媒体凭证并提交 Record；
8. 提交成功的 Record 默认 `VALID`，负责该班级的教师可以追加 `INVALID` 或新的 `VALID` 判断；
9. 责任教师导入和核对官方名单，并在来源或范围错误时回到前一个有效快照；
10. 责任教师确认耐力跑真实用时，系统按当前换算表生成不可追溯改写的分数和等级；
11. 学生提交耐力跑免测、校队或社团认证及图片材料，责任教师审核、要求补充、批准、驳回，并对认证分配或撤销两类认可学时；
12. 系统按照 `P2-STATS-01` 至 `P2-STATS-03` 汇总有效 Record 与认证认可学时，学生和教师查看分类进度、总有效学时和课程完成率；
13. 责任教师填写、发布、修改并重新发布本人教学班学生的 INT 最终成绩和最多 50 字备注，历次发布结果只读保留；
14. 学生提交用户反馈，授权管理员追加公开回复并更新、关闭或重新跟进；
15. 授权管理员创建、编辑、发布、下线和重新上线双语帮助文章，学生只查看当前语言的已发布内容；
16. 总管理员建立分管理员、分配固定八项权限，并执行启停、编辑、职责移交后删除；
17. 授权管理员在 `NORMAL/MAINTENANCE` 间受控切换并发布双语维护公告；
18. 学生和分管理员按既有身份验证与职责阻塞规则注销本人账号；教师账号由管理员核对后删除，删除不转移或改写课程责任关系；
19. 系统对面向用户的正式结果变化生成站内通知中心消息，不发送短信、邮件或 Android/iOS 系统 Push；
20. 系统为关键业务、管理和安全操作写入不可修改的审计事件，授权管理员查询列表和只读详情，并按授权日期范围请求服务器运行日志 ZIP。

学生不能自行创建、自由选择或管理班级；教师不能管理或审核其他教师负责的班级；管理员不负责日常创建班级、生成邀请码或代替责任教师审核。

上述能力都必须进入正式 Domain、数据库、Contract、Backend 和验收，不得只预建业务状态、空表、TODO、空接口、Mock 或 Fake Success。扩展上线范围不恢复已经 `REJECTED` 的学生自由选班、同学期多个有效教学班、手工增加 60 分钟、Record 重提或 attempt 链、模拟扫码成功、合成学生工作区、教师本人注销、总管理员本人注销或依赖短信/邮件/设备 Push 才能完成业务等能力。

### 0.5 核心状态机

运动会话状态机：

```text
ACTIVE ↔ PAUSED → COMPLETED
   └──────────────→ COMPLETED
```

- 开始运动后进入 `ACTIVE`；
- `ACTIVE → PAUSED` 表示暂停，`PAUSED → ACTIVE` 表示继续；
- `ACTIVE` 或 `PAUSED` 都可以结束并进入 `COMPLETED`；
- `COMPLETED` 是终态，不能恢复为 `ACTIVE` 或 `PAUSED`。

正式 Record 与当前审核结果：

```text
提交前本地准备内容（不是正式 Record）
                 ↓ 提交成功
              VALID ↔ INVALID
```

- 提交成功时才形成正式 Record，当前审核结果默认为 `VALID`；
- 教师只能通过追加审核记录使当前结果在 `VALID` 和 `INVALID` 之间变化；
- 正式 Record、媒体、Backend 确认的实际运动时长和历次审核记录均不可覆盖；
- 初版正式 Record 不使用 `DRAFT`、`SUBMITTED`、`APPROVED`、`REJECTED` 或 `resubmission` 作为业务状态。

## 1. 总体业务目标

BNBU Sports 用于管理体育课程、教学班、学生运动、打卡凭证、教师审核、成绩、耐力跑、免测或校队/社团认证、账号安全和系统治理。

系统包含三种基础角色：

- 学生：加入课程、完成运动、提交凭证、查看耐力跑真实用时、打卡总时长和成绩、提交申请；
- 教师：管理本人教学班和成员、核对官方名单、记录耐力跑真实用时、审核打卡和申请、配置分类学时、查看进度参考、填写并发布最终成绩；
- 管理员：只读查看当前全部课程及其学生和打卡汇总、只读查看学生账户资料与状态，并管理学期、教师账号、管理员权限、全局规则、反馈、帮助中心、系统模式和审计查询。

管理员基础角色保持一致，但分为总管理员和分管理员。总管理员负责建立分管理员并分配管理权限；分管理员只能处理被授权的业务范围。

## 4. 已确定的全局业务规则

1. 只有学生、教师、管理员三种基础角色。
2. 管理员内部通过总管理员和分管理员区分治理权限，不新增其他基础角色。
3. 每个教学班只有一名责任教师。
4. 教师直接在当前学期自定义创建并命名课程，不依赖预设课程目录，不填写课程代码或教学班号；管理员不能创建课程。系统使用不可见的内部 ID 区分课程，课程名称用于所有角色的业务展示。
5. 同一学生在同一学期同一时间只能存在一个有效体育教学班；被原责任教师移出后，可以通过新邀请加入其他教学班。
6. 学生通过有效邀请正常加入时直接生效，不经过教师或管理员审批。
7. 官方名单是学校快照，不等于课程成员关系。
8. 学生提交打卡后，打卡记录默认有效。
9. 责任教师可以在发现问题后追加无效判断，也可以追加新的有效判断纠正先前结果。
10. 同一学生、同一教学班、同一业务日期最多提交一条打卡记录；业务日期固定为 Backend 接受 Session 开始命令时 `started_at` 在上海时区的日历日期，跨午夜、暂停、结束或延迟提交都不改变它；记录后来变为无效也不产生第二次当日提交名额。
11. 正式实际运动时长只按运动事实计算，由 Backend 累计全部 `ACTIVE` 区间并完全排除 `PAUSED` 区间；正式业务不提供“增加 60 分钟”。
12. 正式实际运动时长少于 60 分钟计入 0 分钟有效学时；满 60 分钟但不足 120 分钟计入 60 分钟有效学时；达到或超过 120 分钟计入 120 分钟有效学时。正式实际运动时长与计入有效学时必须作为两个不同业务概念处理。
13. 当前学期总打卡目标为 20 小时，达到后停止新打卡，并提示已经完成目标。
14. 教师为本人教学班设置课程相关运动目标和其他运动目标。
15. 两类运动目标合计固定为 20 小时。
16. 校队或社团认证批准后，教师可以为该学生设置两类运动的认可学时。
17. 每类认可学时不能超过该教学班对应分类目标，合计不能超过 20 小时。
18. 每类计入完成量最多达到本类目标，单类超额不能替代另一类未完成部分。
19. 打卡总时长等于两类计入完成量之和，最高为 20 小时。
20. 学生记录界面分别展示耐力跑真实用时和本人打卡总时长，两者不互相折算。
21. 耐力跑免测通过后，耐力跑位置显示免测状态，不为打卡总时长增加学时。
22. 当前 20 小时规则根据有效打卡和认证认可学时生成进度参考；耐力跑真实用时独立展示，不进入该进度参考。
23. 责任教师可以为本人教学班学生填写 INT 最终成绩和最多 50 字备注并发布；当前不限定 0–100 等取值范围，最终成绩不要求等于 20 小时进度参考结果。
24. 打卡审核只使用有效和无效两种当前结果。
25. 系统不提供教师内部备注字段；打卡、免测和认证审核只保存正式审核结果、学生可见原因或学生可见处理意见。
26. 历史课程成员、名单、打卡、凭证、审核、申请、成绩和审计记录不能通过普通页面物理删除。
27. 当前不采集定位、轨迹或地图信息。
28. 所有学生反馈统一进入管理员队列；反馈单始终由有“学生问题反馈”权限的管理员处理。课程问题需要教学事实时，管理员可以另行协调责任教师核查，但当前反馈界面不提供转交、指派或教师处理入口。
29. 帮助中心管理、系统模式切换和学期管理都是正式管理员业务。
30. 面向用户的正式结果变化进入站内通知中心；站内通知是否已读不改变业务结果，系统不发送短信、邮件或 Android/iOS 系统 Push。
31. 教师端不提供本人账号注销。
32. 管理员不能默认代替责任教师审核打卡、填写或发布最终成绩、审批免测。
33. 只有总管理员或具有“审计查询”权限的分管理员可以在本组织授权范围内查询审计事件；学生和教师不访问系统级原始事件或服务器运行日志 ZIP，任何管理员都不能修改、补写或删除审计事件。
34. 管理员系统概览和系统健康检查都是按权限展示的只读观察能力；刷新不改变业务事实，`UP`、`DOWN`、`NOT_CONFIGURED` 必须按实际结果展示，缺失延迟或积压数据不能被表述为健康。
35. 系统模式只有正常和维护两种；切入维护模式必须同时提供中英文维护公告和预计恢复时间，维护模式只保留当前模式、变更历史和模式切换等明确允许的安全治理能力。
36. 正式产品的课程加入只能通过真实扫码或手动输入有效邀请码完成；“模拟扫码成功”、`Fake Success` 或其他预置成功入口不得进入正式产品，也不能建立课程成员关系。
37. 正式产品不得把合成或 Mock 学生工作区作为登录、业务成功或数据回退路径；开发和测试数据必须与正式业务隔离，不能形成正式业务事实。
38. 已提交的运动记录不建立 `resubmission` 重提业务链。记录被判为无效后不生成针对原记录的新尝试；责任教师可以追加新的有效判断纠正原结果，学生只能在下一个符合条件的业务日期创建独立的新记录。
39. 客户端版本策略检查属于启动辅助检查，单个辅助接口本次故障不能独自导致整个 App 无法使用；但本机已经缓存的强制升级要求不能因检查失败被清除、降级或绕过，只有取得新的权威版本策略结果后才能按新结果更新。
40. 官方名单上传只接受 XLSX 或 CSV，单文件最大 100 MB，单次导入最多 500 个人员数据行；表头不计，重复或错误行也计入上限，客户端预检不能代替 Backend 的权威格式、大小和人数校验。
41. 免测和校队/社团认证图片只接受 JPEG、PNG 或 WebP；同一申请的首次材料和全部补充材料合计最多 3 张，单张最大 10 MB。
42. 运动记录、正式媒体文件和审计日志不因账号注销删除。
43. 账号注销成功时删除登录凭据、登录会话、验证码/验证挑战、邮箱、登录名和当前 Profile PII；已经保留的业务事实只通过不含个人信息、不能登录的内部历史主体 ID 关联，不能保留可恢复账号的数据或将旧账号静默恢复。

## 5. 管理员初始化

### 5.1 初始总管理员

系统初始只有一名总管理员。

初始总管理员由系统或他人分配的初始密码属于临时密码。首次登录后只能修改本人密码或退出登录，完成本人改密前不能进入其他管理员业务；本决定不补造此前未确认的初始总管理员密码长度或字符组合规则。

总管理员拥有全部管理员权限，可以：

- 创建分管理员；
- 停用或重新启用分管理员；
- 删除已经完成职责移交的分管理员账号；
- 为分管理员分配或收回权限；
- 只读查看当前全部课程及其学生和打卡汇总；
- 管理学期；
- 只读查看学生账户资料和当前状态；
- 管理教师账号；
- 管理用户反馈；
- 管理全局规则；
- 切换系统模式；
- 管理帮助中心；
- 查询审计事件、查看脱敏详情，并按授权日期范围请求服务器运行日志 ZIP。

总管理员仍受历史保留和责任教师边界限制，不能代替教师创建或管理课程，也不能代替教师处理教学审核。

### 5.2 分管理员

分管理员仍属于管理员基础角色，但只拥有总管理员明确分配的业务权限。

创建分管理员时，总管理员填写全系统唯一且创建后不可修改的账号、姓名、有效且未被其他分管理员使用的学校邮箱、可选所属部门、初始密码和确认密码。初始密码只要求已填写且两次输入一致，不增加长度、字符组合、强度或自动生成规则。该密码属于临时密码；分管理员首次登录后只能修改本人密码或退出登录，完成本人改密前不能进入其他管理员业务。创建前统一核对账号资料和权限摘要，并且至少分配一项业务权限；创建成功后账号默认为 `ACTIVE`。

可分配的权限范围包括：

- 当前课程只读查看；
- 学期管理；
- 用户与账号：学生账户只读查看，以及教师账号建立和删除；
- 用户反馈管理；
- 全局规则管理；
- 系统模式管理；
- 帮助中心管理；
- 审计查询；

可分配业务权限固定为 8 项：课程查看、学期管理、用户与账号、学生问题反馈、全局规则、系统模式、帮助中心和审计查询。总管理员可以自定义选择和组合，也可以使用学生服务、教务运营、规则与系统或只读核查模板快速填写；模板只负责覆盖当前勾选结果，保存前仍可继续增减。系统概览根据已有权限自动展示，不单独分配；分管理员设置不能下放。学期管理、全局规则和系统模式属于高风险权限，确认时必须醒目标识。分管理员不能创建或提升其他管理员，也不能获得责任教师专属业务权限。没有对应权限时，只能查看被允许的摘要或完全不能进入该业务范围。

总管理员编辑分管理员时，登录账号保持不可修改；姓名、学校邮箱、所属部门和业务权限可以更新，学校邮箱仍须有效且唯一。普通编辑不显示或接收密码字段；总管理员不能查看、取得或替换分管理员个人密码，也不存在管理员应急代设路径。分管理员状态只有 `ACTIVE` 和 `DISABLED`：停用后不能继续登录且现有登录状态失效，重新启用只恢复现有已分配权限，不自动增加权限。任何编辑、启停和权限变化都保留更新时间并写入审计历史。

总管理员删除分管理员前必须核对准确账号并完成职责移交。删除后，该账号不再出现在可用管理员列表中，不能继续登录；已经完成的业务记录和审计历史继续保留，不能随账号一起删除。

### 5.3 全局规则管理

具有全局规则权限的管理员维护四套耐力跑换算表：男生大一/大二 1000 米、男生大三/大四 1000 米、女生大一/大二 800 米、女生大三/大四 800 米。管理员只能在当前选中的表内添加、编辑或删除用时区间规则，不能通过规则页面改变学生性别、年级、真实用时、免测状态或教师最终成绩。

每次保存或删除前都必须校验所选整表；用时区间必须连续、无间隙、无重叠，分数必须处于 0 至 100，性别与项目组合必须正确。操作由当前有权限的管理员确认后直接生效，不设置单独启用、停用或二次审批步骤；创建、编辑和删除都写入审计记录，既有学生历史结果不得被追溯改写。

### 5.4 分管理员账号退出与注销

分管理员可以在没有未移交职责时申请注销本人账号。

当前业务流程不处理总管理员离任、失联、本人注销或身份交接。总管理员因忘记密码无法登录时，可以通过已验证学校邮箱完成本人验证并设置新密码。

状态为 `ACTIVE` 的总管理员和分管理员可以在有效登录状态下凭当前密码和最新数据版本修改本人密码；成功后保留当前登录状态、撤销其他登录状态并清除首次改密门禁。总管理员和分管理员也可以通过已验证学校邮箱的一次性挑战自助重置；成功后撤销全部登录状态、不自动登录并清除首次改密门禁。两条路径的新个人密码都只要求非空，不设置最大长度、blocklist 或必须不同于当前密码的限制。

### 5.5 管理员系统概览

系统概览只读展示当前系统模式、唯一当前学期、学生与行政班级资料摘要、教师数量、系统健康状态，以及 1000/800 米换算表的规则数量和适用分组。

概览卡片只能导航到对应业务页面，不能绕过目标页面的权限和操作边界。健康项只接受 `UP`、`DOWN`、`NOT_CONFIGURED` 等明确结果；延迟、积压量或检查结果缺失时显示不可用，不能推断为正常。

## 6. 教师账号建立与登录

### 6.1 批量建立教师账号

具有教师账号管理权限的管理员可以通过 UTF-8 CSV 批量建立教师账号，并为本批账号设置同一个初始密码。必填列为 `employee_id`、`name`、`email`，`college` 可选；学生账户不通过该入口创建。

管理员在批量建立前确认：

- 邮箱是有效的学校邮箱；
- 每个邮箱对应一名真实教师；
- 重复或冲突邮箱不能重复建立账号；
- 正式建立前先校验全部行，任一行错误时整批不能建立；
- 初始密码至少 8 位并包含大写字母、小写字母和数字；
- 初始密码属于敏感信息，只能通过受控方式告知教师；
- CSV 文件、模板、文档和普通业务记录不保存初始密码明文；账号建立后系统不再展示该密码。

### 6.2 教师首次登录

教师使用学校邮箱和统一初始密码登录教师端。

教师首次登录后必须立即设置本人个人密码；完成改密前不能进入其他教师业务。教师更改后的个人密码只属于本人，管理员不能查看。

### 6.3 教师账号边界

- 管理员只读查看教师工号、姓名、职称、学院/部门、状态和详情；状态标签不提供停用、启用或恢复审批；
- 教师不能自行创建其他教师；
- 教师不能查看其他教师密码；
- 教师端不提供本人账号注销；
- 教师离职或不再使用系统时，由管理员删除教师登录账号；
- 删除教师账号不要求先完成责任教师交接，也不建立责任教师交接业务；
- 管理员不能借删除账号修改或转移课程责任教师、管理课程或改写课程事实；
- 删除账号不删除教学班、学生关系或历史责任记录；已有课程与历史继续引用不具登录能力且不含当前账号资料的内部历史主体，历史责任教师快照不能改写。

### 6.4 学生账户只读边界

管理员可以搜索、按状态和学院/部门筛选并查看学生必要资料。学生状态只有 `ACTIVE`（已进班）和 `PENDING`（已绑定并验证学校邮箱但已退班）两种；身份恢复申请与首次邮箱绑定流程都不是学生状态。学生首页只有在状态为 `ACTIVE` 时才能显示体育学时“进行中”，状态为 `PENDING` 时显示“已退班”，旧缓存中的进度值不能覆盖当前学生状态；已经达标的 `ACTIVE` 学生可以显示“已达标”。管理员不能在“用户与账号”页面修改学生资料、角色、邮箱、学生状态、课程关系或登录状态。

## 7. 学期和全局规则准备

### 7.1 学期管理

管理员创建学期后，学期依次经历单向生命周期：

即将开始 → 当前学期 → 已归档

系统同时只能有一个当前学期。`UPCOMING` 学期可继续编辑配置；`CURRENT` 和 `ARCHIVED` 学期只读，归档学期不可恢复或删除。

新建或编辑 `UPCOMING` 学期时填写显示名称、连续学年的 `YYYY-YYYY` 学年、第一/第二/暑期学期类型和日期范围；学年与学期组合必须唯一，结束日期不得早于开始日期。新建学期的课程数和学生数初始为 0。

管理员只能选择已经到达开始日期的 `UPCOMING` 学期，核对原当前学期与新学期后确认切换；尚未到开始日期时必须拒绝切换。切换整体成功后，旧学期自动归档，新学期成为唯一当前学期；不存在单独归档当前学期或恢复归档学期的流程。

已归档学期不恢复，也不删除历史。

### 7.2 运动进度与耐力跑换算

20 小时运动进度规则是当前固定业务口径：教师在教学班内分配两类运动目标，系统据此生成进度参考。当前“全局规则”页面不提供创建、修改、启用或停用 20 小时进度规则的操作。

具有全局规则权限的管理员只在该页面维护 1000/800 米耐力跑换算表。换算结果是耐力跑分数和等级，不计入打卡总时长或 20 小时运动进度，也不限制责任教师填写和发布最终成绩。

### 7.3 当前课程只读查看

管理员通过只读课程目录看板查看当前学期未关闭课程，但不能创建、编辑、关闭或删除课程。看板汇总当前课程数、当前课程有效成员去重后的学生数及责任教师去重后的教师数；每门课程展示课程名称、责任教师、`UPCOMING` 或 `ACTIVE` 展示状态、允许打卡时间、两类运动目标、有效与已移出成员摘要、已提交打卡人数、打卡记录总数、有效记录数、无效记录数、累计与人均计入时长及入班开放状态。管理员页面不展示或要求课程代码、教学班号，也不在该看板打开单条打卡或媒体凭证处理。

课程内容由责任教师管理；管理员只能按课程名称/责任教师搜索，并按全部、进行中或即将开始筛选。查看的数据只用于了解当前教学运行情况，不能借此代替教师执行课程业务。课程管理不设置“已结束”业务状态，也不提供“已结束”筛选或标签；完成率缺少正式完成学生人数时必须显示不可用，不能自行推算。

## 8. 教师建立课程

责任教师：

1. 登录教师端；
2. 选择当前学期；
3. 自定义填写课程名称和必要说明；
4. 确认课程信息准确；
5. 设置允许打卡的日期或时间范围；
6. 设置课程相关运动目标；
7. 设置其他运动目标；
8. 确认两类目标合计为 20 小时；
9. 确认本人是唯一责任教师；
10. 创建课程；
11. 生成二维码或邀请码。

课程开放后可以接收学生加入。关闭后不再接收新学生或新运动，但历史继续保留。

## 9. 学生建立账号并加入教学班

### 9.1 新学生

1. 扫描二维码或输入邀请码；
2. 查看课程名称、教师、学期和邀请状态；
3. 填写姓名、学号、性别和年级；
4. 确认加入；
5. 建立学生身份和有效课程成员关系；
6. 绑定并验证学校邮箱；
7. 进入学生首页。

正式产品不提供“模拟扫码成功”、`Fake Success` 或合成/Mock 学生工作区入口。上述开发或测试能力即使能够展示后续页面，也不能被视为真实加入成功，不能建立课程成员关系或写入其他正式业务事实。

### 9.2 已有学生

已有学生使用已验证学校邮箱和一次性验证码登录，再通过邀请加入教学班。

### 9.3 同学期唯一教学班

学生加入前必须检查当前学期是否已经存在有效体育教学班。

- 没有有效教学班时可以加入；
- 已经存在有效教学班时拒绝加入第二个；
- 原责任教师移出学生后，原有效成员关系结束，学生可以通过新教学班邀请加入；
- 原教学班的打卡、审核、申请和成绩历史不转移。

## 10. 官方名单核对

责任教师通过 XLSX 或 CSV 导入学校确认的官方名单，形成新的名单快照，并与当前课程成员比较。单个文件最大 100 MB，单次最多导入 500 个人员数据行；表头不计，重复或错误行也计入上限。格式、大小或人数任一超限时整次导入失败，不生成名单快照。

教师逐项处理：

- 身份一致的匹配；
- 名单中存在但尚未加入；
- 已加入但不在名单；
- 学号、姓名或身份冲突；
- 重复或不明确匹配。

证据不足时不能自动合并身份。尚未加入的学生仍通过正常邀请加入。

## 11. 学生运动和打卡

### 11.1 开始前条件

学生开始运动前需要满足：

- 账号和学生身份有效；
- 当前学期只有一个有效体育教学班；
- 当前处于该教学班允许打卡的时间范围；
- 没有另一条进行中的运动；
- 打卡总时长尚未达到 20 小时；
- 系统处于允许业务写入的状态。

达到 20 小时后，学生端提示“已达到 20 小时，本学期无法继续打卡”，并停止创建新运动。

### 11.2 运动过程

运动可以在进行中和暂停之间切换，最后进入已结束状态。

正式实际运动时长只来自实际运动过程，由 Backend 累计全部进行中 `ACTIVE` 区间；暂停 `PAUSED` 区间完全排除。断网、切换后台、设备重启或修改设备时间不能直接改变 Backend 认定的正式实际运动时长。

本次运动的业务日期在 Backend 接受 Session 开始命令时固定为 `started_at` 在上海时区的日历日期；Session 跨午夜、暂停、结束或延迟提交都不改变该业务日期，客户端也不能上传或改写它。

正式实际运动时长描述运动事实，计入有效学时描述该事实经过业务分档后对进度的贡献，两者是不同业务概念。任何页面、统计、数据库设计或 Contract 都不能把二者合并为同一字段或互相冒充。

正式业务中不提供“增加 60 分钟”。

### 11.3 计入时长

| 实际持续时间 | 计入学时 |
|---|---:|
| 少于 60 分钟 | 0 分钟 |
| 60 分钟至不足 120 分钟 | 60 分钟 |
| 达到或超过 120 分钟 | 120 分钟 |

单条记录按正式实际运动时长映射出的计入有效学时只有 0、60 或 120 分钟。达到最低门槛的记录只映射为 1 小时或 2 小时，不产生 1.5 小时等小数档；0 分钟档只对应正式实际运动时长不足 60 分钟。Record 当前为 `INVALID` 时不改写原始分档结果，只让该 Record 当前对所有学时统计贡献为 0；恢复为 `VALID` 后继续使用原分档结果。

### 11.4 凭证和提交

学生选择运动分类，填写必要说明，拍摄并保留 0 至 6 张照片和 0 至 1 段 1 至 15 秒且包含音轨的短视频。系统相机或录像界面确认拍摄完成后，素材直接进入本次运动的本地凭证列表，不再增加一次“确认保留”弹窗。学生可以点击任一凭证预览，并在正式提交开始前删除不合适的单项凭证；删除后该本地文件不上传，也不形成正式媒体事实。照片和视频可以同时提交，也可以只提交其中一种，但点击提交时两者合计必须至少保留一项有效媒体凭证。

上线版本图片只允许 JPEG、PNG，单张最大 10 MB；视频只允许 MP4，单段最大 100 MB；单条 Record 的全部媒体文件合计最大 250 MB。数量、格式、单文件大小或总大小任一条件不满足时，该媒体不得进入正式 Record。

Android 和 Web 必须在上传前执行格式、数量、单文件大小和总大小校验，为学生提供即时反馈；Backend 必须在接收或确认媒体时再次执行同一组权威校验，不得仅信任客户端声明或客户端校验结果。只有通过 Backend 权威校验的媒体才能成为正式媒体事实。

正式提交或媒体上传一旦开始，学生不能再从客户端删除该凭证。提交成功后，原记录和正式媒体事实按历史保留规则管理，学生、教师和管理员均不能通过普通业务页面删除或改写。

提交成功后，打卡记录默认有效，对应学时进入当前进度。

同一学生、同一教学班、同一业务日期最多提交一条记录。记录后来被教师判为无效时，当日名额不恢复，学生只能在下一个符合条件的业务日期重新运动。

系统不为已提交记录创建 `resubmission` 或新 attempt。教师纠正错误判断时只追加新的有效判断；学生下一业务日期的提交是独立的新记录，不是对原记录的重提。

## 12. 教师复核打卡

责任教师可以查看本人教学班的打卡记录和媒体凭证。

发现明确问题时，教师追加无效判断并填写学生可见原因。发现先前判断错误时，教师追加新的有效判断；纠正为有效后，该记录原本确定的 60 或 120 分钟重新参与汇总，审核切换不得清零、重算或改写原计入时长。

原记录、媒体和审核历史不能覆盖或删除。教师不能修改正式运动时长，也不能通过审核直接填写任意学时。

## 13. 耐力跑记录

### 13.1 学生端展示

学生记录界面固定展示两个独立内容：

- 耐力跑真实用时及其换算分和等级，或者免测状态；
- 本学期打卡总时长。

两项分别展示，不互相折算。

### 13.2 耐力跑真实用时

女性记录 800 米真实用时，男性记录 1000 米真实用时。真实用时由责任教师根据正式测试结果确认。

当前耐力跑用时不自动转换为打卡学时，也不进入 20 小时运动进度参考。

### 13.3 耐力跑成绩换算

责任教师确认真实用时后，系统根据学生性别、当前年级组和项目选择唯一换算表，并以整数秒在包含上下限的用时区间内匹配一条规则，得到 0 至 100 分及优秀、良好、及格或不及格等级。男生只匹配 1000 米表，女生只匹配 800 米表；大一/大二和大三/大四分别使用各自表。

当前预置规则的 99 分至 1 分区间均按连续 3 秒一档、每档下降 1 分；100 分和 0 分分别覆盖首尾区间。一个具体用时只能命中一个分数区间，不能出现无匹配或同时命中多条规则。

耐力跑换算分和等级只说明该次耐力跑表现，不增加打卡总时长、不进入 20 小时运动进度参考，也不自动成为或改写教师发布的最终成绩。换算表变更只用于后续换算，已经形成的历史结果继续保留。

### 13.4 耐力跑免测

学生提交耐力跑免测申请和证明材料，由责任教师审核。证明材料只接受通过拍照或相册选择的 JPEG、PNG 或 WebP 图片，不接受 PDF、视频或其他文件格式；同一申请的首次材料和全部补充材料合计最多 3 张，单张最大 10 MB。安卓学生端和网页学生端在申请详情中展示已上传图片的缩略图。

批准后：

- 学生耐力跑位置显示免测；
- 不要求显示真实用时；
- 不按普通用时换算表生成分数或等级；
- 不向打卡总时长增加学时；
- 不改变 20 小时进度参考，也不会自动改写教师已发布的最终成绩。

## 14. 校队和社团认证

学生提交校队或社团证明材料，由责任教师审核。证明材料沿用耐力跑免测的图片规则，只接受 JPEG、PNG 或 WebP，同一申请累计最多 3 张、单张最大 10 MB，并在申请详情中展示缩略图。

批准后，教师为该学生自定义认可总时长，并按实际情况分配到：

- 课程相关运动认可学时；
- 其他运动认可学时。

业务限制：

- 课程相关运动和其他运动都可以获得认可学时，任一类可以为 0，不固定只抵扣某一类；
- 每类认可学时不能超过教学班对应分类目标；
- 两类认可学时合计不能超过 20 小时；
- 认可学时进入对应分类完成量和打卡总时长；
- 学生仍需补足没有被认可的分类学时；
- 认证被撤销后，相应认可学时取消，学生需要补足差额；
- 原认证和调整历史继续保留。

## 15. 进度与成绩

学生端展示：

- 课程相关运动目标、实际有效学时、认证认可学时和剩余学时；
- 其他运动目标、实际有效学时、认证认可学时和剩余学时；
- 两类合计打卡总时长；
- 耐力跑真实用时或免测状态；
- 当前达标状态和正式成绩。

每类计入完成量最多达到本类目标。单类超额可以保留在历史记录中，但不能替代另一类目标。两类计入完成量之和达到 20 小时后停止新打卡。

系统根据有效打卡、认证认可学时、分类目标和固定的 20 小时规则更新运动进度参考。

上线统计累计当前审核结果为 `VALID` 的 Record 和当前有效的认证认可学时。每条 Record 先按 Backend 确认的正式实际运动时长映射为 0、60 或 120 分钟有效学时；当前结果为 `INVALID` 时，该 Record 对所有学时统计贡献均为 0；认证被撤销后，其认可学时贡献为 0。系统分别汇总每个运动类别的有效 Record 学时和认可学时，在各类别目标上限处封顶，再将各类别封顶后的结果相加得到总有效学时。

课程完成率按 `min(总有效学时 / 总目标学时, 100%)` 计算。UI 将该比例四舍五入为整数百分比展示；是否达标、是否允许继续打卡以及其他业务判断全部使用原始分钟值，不能使用展示百分比反推。

责任教师可以为本人教学班学生直接填写 INT 最终成绩并发布，可同时填写最多 50 个字符的备注。当前不增加 0–100 等取值范围；教师可以再次修改和重新发布成绩与备注，不需要学生发起调整申请，也不需要管理员审批；历次发布结果继续保留。

## 16. 用户反馈

Android 与网页学生端统一提交问题类型（功能异常、功能建议、无障碍问题、隐私问题、其他）和问题描述。系统把反馈与已登录学生身份关联，生成反馈编号、提交时间和初始状态“待受理”。管理端按同一分类与问题内容展示，并补充提交人姓名、学号和当前学校邮箱。客户端平台、版本、附件、优先级、指定处理人和内部备注不属于当前管理界面的业务字段。

反馈使用五种状态：

| 状态 | 业务含义 |
|---|---|
| 待受理 | 学生刚提交、尚未由管理员开始处理；只作为初始状态 |
| 受理中 | 管理员已经受理并正在跟进 |
| 待技术团队处理 | 问题需要技术团队继续排查或处理 |
| 处理完成 | 已经向学生说明处理结果，当前无需继续处理 |
| 已关闭 | 本轮反馈已经关闭 |

“待处理”统计包括待受理、受理中和待技术团队处理，不包括处理完成或已关闭。管理员首次打开待受理反馈时，处理状态默认选择“受理中”；保存时必须从受理中、待技术团队处理、处理完成或已关闭中选择当前状态，并同时填写一条学生可见的公开回复。待受理不能被重新选择。

每次保存都追加一条包含处理人、回复内容和处理时间的记录，并记录状态变更审计；已有处理记录不得覆盖或删除。处理完成或已关闭的反馈确需继续跟进时，可以重新设为受理中或待技术团队处理，但必须追加说明原因和下一步的公开回复。

反馈统一留在管理员队列。课程问题需要核查课程成员、名单、打卡、耐力跑、认证或成绩事实时，管理员可以另行协调对应责任教师，但当前反馈界面不建立转交关系、不指定教师为处理人，也不把状态和公开回复权限交给教师。管理员仍负责向学生回复并维护反馈状态。

反馈处理只记录问题沟通和处理进度，不能直接修改课程成员、打卡审核、耐力跑、认证、成绩、申请、账户状态或课程关系；需要改变这些正式业务事实时，必须回到对应业务流程并由有权限的角色操作。

## 17. 帮助中心

帮助中心管理是正式管理员业务。只有总管理员或具有“帮助中心”权限的分管理员可以管理帮助文章；文章受众是学生，教师不负责创建、编辑、发布、下线或重新上线系统帮助文章。

帮助文章使用三种状态：草稿 `draft`、已发布 `published` 和已下线 `archived`。新建文章可以保存为草稿，也可以在满足发布条件时直接保存并发布；后续只允许草稿发布、已发布文章下线、已下线文章重新上线，不允许回退为草稿，也没有物理删除入口。

每篇文章同时维护中英文标题、中英文正文、关键词、分类和排序权重。保存任何状态至少要求中英文标题、分类和有效数值排序权重；草稿允许正文或关键词尚未完整，发布前必须补齐中英文正文并至少提供一个关键词。正文允许输入 Markdown 文本，但管理预览只负责核对当前选择语言的内容，不承诺最终客户端的具体排版效果。

管理端可以查看三种状态的数量，按中英文标题或关键词搜索，按状态和固定分类筛选，并按排序权重和更新时间查看文章。搜索、筛选、分页、切换中英文预览和取消编辑都不改变业务事实；关闭存在未保存修改的编辑器前必须提示这些修改将被放弃。

学生只取得当前语言下已发布的文章；草稿和已下线文章不属于当前公开内容。已发布文章保存编辑后继续保持已发布并直接更新当前公开内容；下线只停止公开展示，不删除文章、首次发布事实或审计历史，重新上线继续使用同一文章。

帮助文章只能解释已经确认的业务流程，不能创建新权限、改写课程或成绩事实、承诺尚不存在的能力，或包含密码、验证码、凭据和不必要的个人信息。“维护期间操作”分类的普通帮助文章不等于系统模式产生的实时维护公告。

创建、更新、发布、下线和重新上线成功后必须保留操作者、时间、前后内容或状态及结果；失败、版本冲突或非法状态转换保持原文章和原状态，不得伪造成功。系统不提供删除、定时发布、版本回滚、发布审批或发布通知流程。

## 18. 系统模式

系统模式管理是正式管理员业务，只有总管理员或具有“系统模式”权限的分管理员可以操作。系统只有以下两种全局模式：

| 模式 | 枚举 | 业务效果 |
|---|---|---|
| 正常模式 | `NORMAL` | 全部已开放业务按既有身份、权限、资源归属和对象状态正常运行 |
| 维护模式 | `MAINTENANCE` | 暂停普通学生和教师的业务访问并展示维护公告；管理员控制台只保留当前模式、变更历史和模式切换等明确允许的安全治理能力 |

系统模式页的当前状态区以只读形式展示模式名称与枚举、策略版本和最后更新时间；“刷新状态”只重新取得当前事实，不触发模式变更。当前模式不能再次作为目标；授权管理员只能选择另一种模式，弹窗先展示“当前模式 → 目标模式”，并要求填写说明原因、影响范围和恢复条件的变更原因。

切换到维护模式时，还必须同时填写中文标题、英文标题、中文正文、英文正文和预计恢复时间；这些中英文内容随切换同步发布，并在维护期间向受影响用户展示。预计恢复时间是告知信息，不是自动恢复指令；系统继续保持维护模式，直到授权管理员明确切换到正常模式。切回正常模式后向受影响用户生成辅助恢复通知，但通知是否送达不作为恢复成功依据，仍以重新取得的当前系统模式为准。

确认切换后立即应用目标模式；取消、校验失败或执行失败均保持原模式，也不生成成功变更历史。模式切换不会删除、覆盖或重算既有课程、成员、打卡、审核、成绩、反馈或审计事实。学生和教师不能通过本机时间、缓存、旧页面或重复请求绕过当前模式。

每次成功切换追加只读历史，至少展示变更原因、变更前后模式、操作人、变更时间和维护公告是否已发布；历史不能编辑或删除。模式切换仍须遵守统一鉴权、权限、幂等、并发版本、审计和失败不伪造成功规则。

## 19. 审计日志与运行诊断

正式审计日志属于上线范围。系统必须生成审计事件并提供列表、只读详情和服务器运行日志 ZIP；总管理员以及具有“审计查询”权限的分管理员可以进入。

“审计日志”是管理员查询入口，“审计事件”是其中一条不可变事实；其他章节中的“审计记录”或“审计历史”均指这些事件的保留集合。审计查询只能覆盖当前管理员获准访问的组织范围，筛选值、请求标识或对象标识不能扩大权限。学生和教师即使是事件中的操作人或事件涉及本人课程，也不取得系统级原始事件的查询权。

审计事件按发生时间从新到旧展示。列表和只读详情用于回答何时、由谁、执行了什么操作、作用于哪个对象、结果如何以及对应哪个请求；缺失字段显示为不可用，不能补造。详情只展示排查所需的安全结构化元数据，不得出现密码、验证码、Token、凭据、原始幂等键、原始 IP、原始设备指纹、完整个人资料、媒体内容、内部存储信息、签名下载地址、内部备注或原始业务快照。

服务器运行日志 ZIP 是独立的运行诊断归档，不是当前审计表格的 CSV 或可编辑副本。它按授权日期范围由服务器异步汇总应用日志、健康摘要、请求关联和审计事件，服务端完成脱敏后才能签发短时下载链接；生成失败、取消、过期或链接无效时不得下载，也不能由浏览器拼接本地替代文件。

查询、筛选、清空条件、刷新、翻页、查看详情和请求诊断归档都不能修改业务事实或审计事件。无结果只表示当前条件下没有匹配项；加载、详情、翻页或归档失败时保留已经取得的有效信息并明确失败，不得显示假成功。

## 20. 站内结果

用户可以在对应业务页面查看正式结果，并在站内通知中心查看面向本人的结果变化提示，例如：

- 课程成员状态；
- 打卡有效或无效结果；
- 认证和免测结果；
- 耐力跑真实用时；
- 成绩发布结果；
- 反馈处理结果；
- 系统维护和恢复结果。

系统不发送短信、邮件或 Android/iOS 系统 Push。站内通知是否已读不改变任何业务事实；业务是否完成仍以对应业务页面的正式状态为准。

## 21. 学期结束

责任教师完成名单、打卡、认证和成绩收尾后关闭教学班。

目标学期已经到达开始日期后，管理员确认切换，系统自动归档旧当前学期。归档不删除任何历史，且不改变教师、学生已经完成的业务事实。

## 22. 已删除的业务

以下内容不再进入正式业务流程：

- 学生“增加 60 分钟”；
- 学生发起成绩调整申请和管理员成绩调整审批；
- 教师本人账号注销；
- 一个学生在同一时间保持多个有效体育教学班关系；
- 达到 20 小时后继续新打卡；
- 把耐力跑真实用时折算为当前打卡总时长；
- 依赖额外通知或设备推送才能完成业务。
- 恢复同一业务日期的第二次打卡机会；
- 对已提交运动记录建立 `resubmission` 重提或 attempt 链；
- 在正式产品中提供“模拟扫码成功”、`Fake Success` 或合成/Mock 学生工作区入口；
- 总管理员离任、失联、本人注销或身份交接处理。

## 23. 最终确认的边界

- 教师使用统一初始密码首次登录后，必须先设置本人个人密码，才能进入其他教师业务。
- 初始总管理员和分管理员使用由系统或他人分配的初始密码首次登录后，也必须先修改本人临时密码，才能进入其他管理员业务。
- 耐力跑真实用时及其换算分和等级独立展示，不折算学时，也不进入 20 小时运动进度参考。
- 两类运动目标由责任教师设置，合计固定为 20 小时。
- 默认有效记录后来被判断为无效时，当日提交名额不恢复；系统不提供恢复当天第二次打卡机会的机制。
- 学生被原责任教师移出后，只要当前没有有效体育教学班，就可以加入其他教学班。
- 责任教师可以填写 INT 最终成绩和最多 50 字备注并直接发布给学生；当前不增加 0–100 等取值范围，也不需要管理员审批。
- 总管理员忘记密码时可以通过已验证学校邮箱找回；离任、失联、本人注销和身份交接仍不属于当前业务流程。
- 照片和视频允许在同一条打卡中同时提交。
- 维护模式下允许具有系统模式权限的管理员切换到正常模式；预计恢复时间本身不会自动切换模式。
- 总管理员可以自定义组合分管理员的管理权限。
- 管理员只能查看当前全部课程及其详细信息、学生人数和打卡情况，不能创建或管理课程。
- 具有全局规则权限的管理员直接维护四套 1000/800 米换算表；当前页面不改变固定的 20 小时进度规则，也不审批教师最终成绩。
- “打卡总时长”名称保持不变；学生提交成功后记录默认有效，认证认可学时继续按既定规则计入对应分类完成量。
